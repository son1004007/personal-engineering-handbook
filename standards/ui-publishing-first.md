# UI 퍼블리싱 우선 설계 검증 기준

- 상태: 제안 초안 (개별 독립 검수 및 규칙 승인 전)
- 제안일: 2026-10-09
- 적용 범위: 사용자가 직접 조작하는 웹/모바일 UI가 있고 화면 흐름이나 정보 구조의 불확실성이 높은 개인 또는 적법하게 승인된 프로젝트
- 출처: 실제 Public Bid Agent 설계 검증에서 도출된 사용자 명시 요구
- 상위 정책: [REVIEW_POLICY.md](../REVIEW_POLICY.md) 및 프로젝트별 정책 우선

## 목적

**설계를 작성한 뒤 백엔드부터 대규모로 구현하지 않고, 먼저 화면 퍼블리싱을 제작하여 사용자가 직접 보고 조작하게 함으로써 설계의 적합성을 더 정확히 검증한다.**

글로만 작성된 요구사항과 아키텍처로는 탐색 구조, 중요 정보의 위치, 사용자 입력·오류·빈 상태, 권한별 화면, 모바일 사용성 등의 결함이 드러나지 않을 수 있다. 실제로 조작 가능한 UI가 있으면 설계와 사용자 행동의 차이를 조기에 발견해 백엔드 API/DB 설계 변경 비용을 줄일 수 있다.

이것은 사용자 검증을 빠르게 하는 **작업 순서의 기본 권고**이며, 검증 전 UI를 제품 완성이나 서버 보안 검증 결과로 해석하지 않는다.

## 권장 흐름 (사용자 화면이 핵심인 경우 SHOULD)

```text
사용자 문제와 핵심 요구사항/수용 기준
-> 주요 화면과 사용자 흐름에 대한 최소 설계
-> UI 퍼블리싱(실행 가능한 화면/상호작용 목업)
-> 사용자가 직접 시연/사용해 화면 구성·문구·정보 흐름 검증
-> 피드백 반영·화면/요구사항/API 데이터 계약 조정
-> 관련 백엔드·인증·DB·외부 연동 구현
-> 자동 테스트·독립 검수·통합 검증
-> 필요한 사용자 재검증과 출시 게이트
```

화면/기능 단위로 애자일하게 반복한다. 모든 화면을 한꺼번에 완성하거나 퍼블리싱 승인 때문에 안전한 별도 구현을 무기한 대기시킨다는 뜻은 아니다.

## 퍼블리싱 산출물의 최소 기준

1. 실제 클릭 가능한 탐색/상세/입력/확인 흐름과 이동 경로. 화면별 입력·출력·상호작용·예외 처리.
2. 로딩·0건·오류·권한 없음·비활성·모바일 레이아웃 등 **해당 기능과 관련된 상태**를 재현할 방법.
3. 실제 서비스 연결 없이도 실행되는 합성 fixture/mock mode. 운영 데이터, 회사/고객 비공개 자료, 비밀정보는 사용하지 않는다.
4. UI에 표시하는 **검증된 사실 / 사용자 입력 / 모델 제안 / 확인되지 않은 상태**가 서로 구분되는지 확인.
5. 사용자가 재현 가능한 실행/미리보기 방법, 화면별 검토 질문, 피드백/결정 기록.
6. mock data/버튼/페이지가 실제 서버 저장·공식 인증·AI 수행처럼 보이지 않도록 눈에 띄는 안내.

퍼블리싱은 React, 정적 HTML 또는 기존 프로젝트 기술로 만들어도 된다. 별도 도구/프레임워크 도입은 효익이 확인될 때만 한다.

## 설계 검증 질문

- 사용자가 첫 화면에서 해결하려는 문제와 다음 행동을 알 수 있는가?
- 목록 → 상세 → 비교/작업/결과 흐름이 불필요한 단계 없이 이해되는가?
- 서비스의 핵심 판단 근거·주의사항·미확인 정보가 적절한 우선순위로 표시되는가?
- 입력 항목과 기술/사업 용어를 실제 사용자도 이해할 수 있는가?
- 검색 0건, 오류, 작업 지연, 권한 거부, 모바일/키보드 사용 상황이 설계와 맞는가?
- 화면에서 확인된 요구와 실제 백엔드 데이터/API 계약 사이에 불일치가 있는가?

## 승인과 예외

- 특정 프로젝트에서 사용자가 **퍼블리싱을 먼저 검증하겠다**고 정했다면 그 프로젝트의 백엔드 UI 의존 기능 착수 전에 피드백을 반영한다. 선행 backend skeleton/fixture/보안 연구가 이미 존재해도 삭제하거나 다시 만드는 것은 아니다.
- 외부 UI가 없는 CLI/library/batch/headless backend, 확정된 표준 UI 또는 작은 긴급 수정은 `N/A` 또는 순서 조정 가능하다.
- 인증·권한·개인정보·결제·데이터 마이그레이션 등 고위험 서버 기능은 UI 승인을 받았다는 이유로 통제를 생략할 수 없다. 중요한 설계의 독립 검수와 최종 독립 리뷰·출시 게이트는 상위 `REVIEW_POLICY.md`를 따른다.
- 퍼블리싱 승인 상태는 `UI_PROPOSED / USER_FEEDBACK_PENDING / UI_APPROVED / REWORK_NEEDED`처럼 기록할 수 있으나, 승인받기 전에는 임의로 `UI_APPROVED` 처리하지 않는다.
- 대표적인 개인 프로젝트의 검수용 임시 화면은 public GitHub에 코드를 기록할 수 있어도 실제 사용자용 공개 서비스 배포와는 구분한다.

## 확인/기록

- 요구사항과 연결된 화면 목록·사용 흐름
- 실행 가능한 퍼블리싱 위치 및 실제 검증 환경
- 피드백/결정(무엇이 타당하고 어떤 것이 바뀌었는지)
- 후속 API/데이터/인증 계약 영향 및 백로그 반영
- 테스트·독립 검수·배포 결과 각각의 상태
